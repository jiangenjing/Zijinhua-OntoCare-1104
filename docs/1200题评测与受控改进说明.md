# 当前客服工作台：评测、真实改进与尚未通过的验收

**截至本次实测，严格来源 ID 首条命中率的 90% 验收未通过。**第一次冻结最终集为 88.0%，新来源预留集为 87.0%。这些失败保留在结果中；验证集的 94.3% 不能代替最终结果。当前网站提供实验版本，不能表述为“真实问题解决率达到 90%”。

## 1. 借鉴 Palantir 的是什么

参照 [AIP Evals 总览](https://www.palantir.com/docs/foundry/aip-evals/overview)、[创建评测套件](https://www.palantir.com/docs/foundry/aip-evals/create-suite)、[实验对比](https://www.palantir.com/docs/foundry/aip-evals/experiments)：为每条测试保存输入、预期、目标函数、评测器与通过条件，对版本做逐题比较，并保留多次运行的波动。官方这些说明没有要求所有项目都必须凑到一千条。

我们迁移的是评测方法，并没有使用 Palantir 商业平台，也不是复制一套“Palantir 官方安克数据集”。数据规模要服从业务覆盖、来源独立性和测量精度；把同一案例翻译几遍不能变成多个独立客户。

## 2. 数据规模与隔离

- 知识库有 875 条 Q&A，其中 872 条允许客户召回，隐藏的 3 条不进入召回。
- 将规范化正文重复、规范化标题相同的记录归为同一来源族，共 776 族；排除没有充分文本或属于比较问题的 26 族。
- 首批选择 600 族，每族生成同一语义的中英文问题，共 **1,200 条问题形式**。开发 300 族／600 形式，验证 150 族／300 形式，最终 150 族／300 形式。
- 在最初划分时另预留 150 族。第一版最终失败后，第二版候选在原开发／验证集上选择，再对这 150 族生成、冻结并测试中英文问题，共新增 300 形式。该预留集只有剩余的五种型号，不能冒充全产品抽样。
- 总计 **750 个来源案例、1,500 个问题形式**，不是 1,500 个真实独立工单。原有 63 封首封邮件是已见回归材料，不能当独立最终测试，也没有完整结案标签。
- 问题由现有 DeepSeek 从原始 Q&A 生成，保留来源、正文哈希和支持片段；支持片段按空白、大小写规范化后检查。机器标签仍需独立人工复核；更广义的语义近似来源可能未被完全隔离。

检索权重提案只接触开发失败。验证集是候选选择集，不叫盲测。回复校验修复还参考了已见验证回放，因此最后的 72 场景质量分数尤其不能称为独立测试。两份检索最终集均在各自代码冻结后打开一次，不将最终逐案失败继续喂回改进器。原始资料作为 RAG 检索库始终可用，这不同于把测试问题和标准标签交给候选生成器。

## 3. 指标与实测结果

### 检索

| 同一测试集内的配对比较 | 原始检索 Hit@1 | 改进 Hit@1 | 状态 |
|---|---:|---:|---|
| 首次最终集，300 形式／150 来源 | 68.3% | 改写＋混合检索 88.0% | 未过 90% |
| 新预留集，300 形式／150 来源 | 61.0% | 再加入保守证据核验 87.0% | 未过 90% |

两个集合分布不同，不能把 88%→87% 连成同题进化曲线。在新预留集，移除证据核验后只有 77.3%，说明该组件在这批相同问题上带来约 9.7 个百分点的提升。相对原始检索，配对提升为 26.0 个百分点，来源族重采样的 95% 区间约为 20.7～31.3 个百分点；仍有 7 条问题从原本命中变为未命中。它支持“本基准上有改进”，不证明线上因果效果或真实结案率。

这里的业务提问级 Recall@1 实际是 **Hit@1：首条是否命中至少一个冻结的可接受来源**。真正的资料集合 Recall@1 是“首条命中的标准资料数／全部标准资料数”。多个来源均可接受时，二者不同。新预留集集合 Recall@1 为约 85.7%；Hit@3 约 94.7%，Hit@5 为 96.0%。两个口径都保留。

另有不看版本与原标准来源的机器证据可答性审计：264/293 条已完成，7 条未完成。90.1% 只是已完成审计上的另一种机器估计；按全部 300 条保守计算是 88.0%。它没有重标冻结答案，也不能用于宣布严格 Recall@1 达标。

### 回复、流程与效率

从验证集预先按型号选 30 个来源族，保留中英文共 60 个问题，再加入 12 个业务／边界／多轮场景，共 72 个场景、74 次 HTTP 请求。四个运行版本使用相同抽样，保留所有原始输出和失败。

初始三组仅控制检索组件，当前试用版还修复了未知型号澄清校验与一次结构化输出重试。因此最终试用版的整体差异不能全部归功于检索。

| 版本 | 流程通过 | 模型回复完成 | HTTP 平均／P50／P99 |
|---|---:|---:|---|
| 原始检索对照 | 63/72 | 68/72 | 6.20／5.91／12.95 秒 |
| 改写＋混合检索 | 68/72 | 69/72 | 7.18／6.72／12.78 秒 |
| 加入证据核验 | 68/72 | 70/72 | 6.94／6.72／11.39 秒 |
| 当前试用版：再修复输出校验 | 72/72 | 72/72 | 6.33／6.45／11.27 秒 |

**72/72 是已见验证场景的一次机器裁判回放，不是未见盲测或真实问题解决率。**温度为零仍存在上游模型波动，不能以单次全过宣称长期可靠。

请求时延从本机 HTTP 发起到完整 JSON 返回，包含实际检索、图遍历、生成与重试，不是 TTFT，也不包含外网浏览器链路。小样本 P99 仅作描述。当前图搜索平均约 0.48 毫秒，但这不包括文本向量检索、查询改写和模型生成。

当前试用版 74 次请求累计约 501,975 推理 token，包含返回了使用量的查询改写、证据核验、回答与重试。裁判、出题和 Ragas 另计；网关单价未核实，不能编造货币成本。缓存热运行不等于新问题首次请求：额外模型调用缓存对照的 6 对固定中文问题中，冷平均 10.74 秒、热平均 7.43 秒；本地编码器已加载，不是冷启动 SLA。

### Ragas 与业务指标

实际运行 Ragas 0.4.3，每版本使用固定 6 个来源族／12 个双语问题对应的英文真实回复。忠实度使用模型实际收到的 FAQ 标题、型号、正文、用户输入和系统／Skill 权限；上下文精度、召回只评实际召回的 FAQ。修复评测输入漏掉标题和权限信息之前的正文单独评分保留为诊断，不把评测器修复当模型提升。

原始检索与改写＋混合检索的 Faithfulness 分别约 83.5%、91.1%，Context Precision 约 68.5%、97.2%。当前试用版的 Faithfulness 为约 89.0%，Context Recall 100%，Context Precision 94.3%，Answer Relevancy 93.2%（每项 n=12）。当前忠实度并没有全面优于所有前序版本；单次裁判流程全过也没有消除残余幻觉风险。完整分项、逐原子断言理由在结果文件中。Ragas 不提供这里所谓唯一的“官方综合分”，本项目不伪造一个。

没有真实结案、转接回执、CSAT 问卷和客户关联的重复咨询结果，因此真实问题解决率、实际转人工率、CSAT、重复咨询率保持缺失。只能测“回复中建议人工核查”的代理比例。

## 4. LLM Judge 实际怎么打分

使用现有授权的 **DeepSeek-V4.1-Flash** 单独调用，隐藏版本名与此前分数；主模型也是该服务。不是 Gemini，也不是独立人工或独立模型供应商，存在同源偏差。

五维各 0～2 分，每维均保存具体理由：

1. 事实与型号准确性；
2. 证据支持；
3. 处理步骤与历史状态；
4. 业务条件与权限边界；
5. 表达清晰度与中英文一致性。

流程通过还要求总分≥8、实际任务被回答、模型完成、程序硬检查全过、预期工作流一致，并且事实、证据、业务边界没有零分。模型给 10 分但代码校验失败，仍然不通过；页面单独列出硬门控原因。每次均保留成功理由、Bad Case 理由和归因层。

五维 Judge 是本次抽样批量评测的单独调用，当前不是每条在线客户消息都触发。在线的证据核验只负责排序，和回复质量裁判是两件事。上线后可对风险场景和抽样轨迹异步打分；增加在线核验通常增加延迟，不能称为天然的时延优化。

4 个明显正负控制样例的裁判判断全部符合预期，但这只是小规模校准，不能代替人类金标准。另提供 20 组版本匿名打乱的前后回答抽检包；审核人、结论与理由保持空白，不把助手复核冒充人工确认。

## 5. 具体改了什么

- **识别／校验：**修复中文紧邻型号的识别；已明确来源的配件编码不当作另一台主机。未知型号的澄清可复述用户原编码，不能凭空引入新型号。非法结构化回复最多反馈重试一次；鉴权失败仍如实展示，不包装成模型已完成。
- **检索算法：**先按型号和明确错误码筛选；以 E5 标题余弦、正文窗口最大余弦和饱和 BM25 标题分加权，权重为 0.35／0.50／0.15。不是训练 DeepSeek 参数。
- **检索 Prompt：**中文查询转英文，保留编码、数字、否定和已完成步骤，不给改写器任何 FAQ、答案或标准标签。
- **证据核验 Prompt：**在召回的真实候选里查证首条是否足以回答；足够则保留，缺证据／主题错误才重排。模型只能选择现有来源，不能创造来源或越过型号条件。激进“总选最贴切”的重排在验证集下降，已拒绝。
- **缓存：**查询改写绑定输入、模型、提示词；证据核验绑定问题、完整候选内容、模型和提示词；FAQ 缓存区分运行模式与检索版本；本体缓存沿用版本／内容边界。
- **图搜索：**沿用产品范围内两跳 BFS，最多 30 个概念、6 条证据，记录节点、边、路径、约束和来源，不从产品中心节点无限扩散。是约束导航，不是通用逻辑推理机，没有新引入 Leiden、GNN 或 OWL 推理器。
- **本体与 MCP：**业务本体事实与政策沿用当前版本，客服仍通过受约束工具取得知识、订单和经销商依据。MCP 是工具访问协议，不会自动带来正确检索或业务推理。

## 6. 自进化如何验收

本次尝试了 7 个检索配置／改写候选及 2 个证据重排策略。模型确实基于开发失败给过权重提案；其余为受控工程候选。全过程是“轨迹→坏例→归因→局部候选→开发／验证→冻结→独立测试→接受或拒绝”。这包含检索、上下文 Prompt 与运行校验的改进，没有做参数微调、RLHF、DPO，也没有让系统自行修改售后政策。

所有候选都画入曲线，未测验证点留空。只有这些候选，不能宣称历史曲线已经长期收敛。两次严格最终结果均未达到绝对门槛，因此自动流程状态是 `needs_independent_labels_or_new_tickets`。下一轮应先独立复核可接受等价来源和歧义资料，再获取新真实工单；不能不断修改标准答案、重用最终集，直到偶然超过 90%。

当前机器裁判存在具体争议：例如来源将“异常解除”表述成 lifted，回复可能误解为盖板物理翘起；另有“条件检查”被说成“最可能原因”的过度断言。它们进入来源／答案待复核队列，不能因为总体通过率高而忽略。

密钥与原始工单、订单资料留在本机。包含历史邮件片段的 `evaluation/customer-service-v2` 及相关历史结果已加入忽略规则；私有评测分支仅打包构造 Q&A 数据、非原始工单的行为场景、Q&A 回复与评分、聚合指标。回放订单及 63 封邮件仍需本机导入的原比赛资料。上游模型服务没有提供可冻结的权重版本，保存请求模型名、提示词、源文件哈希和返回使用量仍不能保证未来完全逐字重现。
