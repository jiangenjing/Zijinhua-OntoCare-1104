# OntoCare 智能客服：技术架构与实现

> 依据 2026 年 11 月 3 日本机工作台代码与已保存的评测记录整理。本文描述当前实现及其边界，不将实验方案等同于已上线能力。

## 一、项目定位与总体架构

OntoCare 面向安克跨境售后中产品型号多、知识分散、售后条件复杂的问题，构建可追溯的客服 Agent 和本体工作台。系统将产品、故障、FAQ、订单和服务条件组织为业务结构，在检索时限定型号和资料范围，再结合 Skill、会话状态与决策规则生成答复。

整体采用 Python、Flask 和本地 SQLite。前端包含客服对话、对话关联图、本体拓扑、类／关系／实例浏览、评测和经营报告。后端由数据与本体、检索、客服 Agent、业务决策、模型调用和评测等模块组成；外部 Agent 可通过 MCP 访问受限工具。当前服务是本机演示，订单和物流是比赛资料快照。

```text
业务资料 → 清洗与来源记录 → 双本体和文本索引
                                 ↓
用户问题 → 意图与型号识别 → 混合召回 → 局部图搜索
                                 ↓
                   证据＋会话状态＋Skill＋规则
                                 ↓
                      LLM 生成 → 校验与 SOP
                                 ↓
                   答复／追问／本地人工待办
                                 ↓
                   轨迹、评测、候选改进与回归
```

## 二、数据处理与本体构建

输入为 FAQ／Q&A、客诉首封邮件、订单商品、物流、经销商和赛题 SOP。`ontocare/data.py` 使用 openpyxl 与 Excel XML 读取数据，按真实合并区域恢复共享字段，核对总表和拆分表，提取 PN、SKU 等字段，并保留文件哈希、工作表和原始行号。当前资料包含 875 条 Q&A，其中 872 条允许客服召回；附件仅登记，未宣称已经理解其内容。

本体采用 Schema-first 方法：工程侧先定义产品型号、知识、错误码、检查动作、订单、商品、包裹和条件等类型，再由程序通过 PN、SKU、订单号、字段映射及限定正则生成实例和关系。FAQ 的 PN 字段用于建立“型号—适用知识”；标题中明确出现的部分错误码及正文中符合规则的检查动作形成关联。来源不明确的映射保持待核查，不由模型补造。

底层沿用 EvoOntology 的 Term、Mapping、Evidence、Constraint 与 Relation 语义记录：Term 表示概念，Mapping 指向数据位置，Evidence 记录原文及来源，Constraint 限定适用型号和条件。`ontology.py` 构建并校验版本，`business.py` 另建订单等业务投影；SQLite 保存业务和会话快照，语义版本以文件保存。

系统将业务底座分成两个视图：Service Ontology 组织“型号—故障—知识—检查动作—证据”；Decision Ontology 组织业务条件、规则、缺失事实及动作边界。两者由对象 ID、查询结果和代码侧决策函数／状态机衔接。图关系用于定位和组织依据，售后政策仍需核对来源、适用范围和条件。

## 三、索引、意图识别与混合检索

FAQ 标题和正文窗口使用 `intfloat/multilingual-e5-small` 编码，向量做 L2 归一化并保存在本地 NPZ；正文以最多 200 个空白分词为窗口、步长 160，生成回答时仍读取完整父 Q&A。索引覆盖可见资料，补抓的官方正文在检索后按父 FAQ、哈希和型号范围挂接，不能认为所有补充正文都已进入向量索引。

客服主入口由 `customer_workflow_agent.py` 组合基础 Agent 与 SOP 状态机。`intent_router.py` 先用有序关键词和正则识别物流、排障、退款等明确意图；遇到隐含或混合表达时，可调用模型输出结构化分类，并校验 JSON 和原文证据。模型证据缺失或置信度低于 0.75 时要求澄清；该阈值是工程配置，不代表经过校准的概率。PN、错误码和订单号主要通过正则及别名表识别，型号不唯一时追问。

知识问答首先通过规范 PN 定位本体对象，限定适用知识范围。中文问题可在约束下翻译成英文检索表达，并检查型号和数字是否保留。当前在线排序在型号和可解析错误码范围内，将 E5 标题相似度、正文窗口最高相似度及标题 BM25 归一化得分按 0.35、0.50、0.15 加权，默认取前 6 条；随后可由 LLM 在已有候选中选择最合适的首条，不能新造来源。

## 四、局部图搜索、生成与业务约束

`graph_search.py` 将命中的 FAQ 映射成知识节点，在同型号、有效状态的本体范围内进行多源广度优先搜索（BFS）：最多两跳、30 个概念和 6 个证据种子；遍历到产品中心节点时不再继续扩散。结果包含节点、边、路径、数据映射和约束。文本召回在前，BFS 对召回结果补充关系；当前未使用 Leiden 社区检测、Graph Embedding 或通用 OWL 推理机。

Agent 把用户问题、会话历史、FAQ 原文、可用官方正文、局部图、订单／渠道快照和对应 Skill 组装成上下文，调用 DeepSeek 生成中英文结构化回复及引用 ID。模型可在预算内调用受限的知识检索或本体解析工具。系统随后检查引用来源、型号范围、内容哈希及未经核验的退款／换货承诺；部分失败可重试，否则保留失败状态并使用保底回复。

售后条件由 `decisions.py` 和 `customer_workflow.py` 中的规则及状态机判断。客户陈述与独立核验分开；缺少订单、目标商品或材料时进入追问或本地复核。当前没有真实退款、换货、物流查询或发信接口，本地待办不等于外部操作成功。SOP 状态机在部分多轮场景会重复确认、覆盖具体答复，仍需修复。

## 五、缓存、工作台与 MCP

本体缓存绑定版本及文件状态，复用已校验快照、概念解析和局部图查询；查询翻译、证据重排和少量固定 FAQ 也有对应缓存。它们是应用层计算或结果缓存，不是 Transformer KV Cache，也不能跳过型号适用性和业务权限检查。

工作台通过 `manager.py` 提供类、属性、关系、实例和拓扑视图；用户可查看节点、关联依据及来源。客服页显示本轮对话与实际关联对象。`service_api.py` 封装知识、对象、订单和决策等工具，`service_mcp.py` 通过 MCP 暴露给外部 Agent；网页主流程直接调用项目内部 Python 逻辑，MCP 本身不是检索算法。

## 六、评测与受控改进

评测结合程序硬检查、LLM Judge 和多轮对抗测试。Judge 对事实与型号、证据支持、步骤与历史、业务边界、表达及中英文一致性五维各打 0—2 分；还需任务满足、关键维度非零及硬检查通过。记录包含回答、引用、工具事实、逐维理由和版本，便于定位资料、映射、检索、Skill、状态机或裁判问题。

一次 63 封已见真实首封邮件回归中，首轮回复与流程通过 51/63（80.95%）；另有三组构造的五轮对话，全程通过 0/3。五条样本重复评分的通过判断一致率为 5/5，逐维分数一致率 84%；三条虚构退款完成的构造负例均被识别。主模型和裁判同系列，人工校准仍待完成；这些结果不是独立盲测，也不能当作真实结案解决率。该 63 封未建立人工 gold 知识集合，不能报告其 Recall@1。

`evolution.py` 提供宿主辅助、范围受限的 Skill 候选和配对评测门控：根据失败轨迹提出局部修改，经来源、结构、策略兼容和回归检查后决定是否采纳；版本可回滚。当前不是模型参数的 RLHF，也不是自主修改全部 Schema、工具和策略。项目后续重点是修复多轮流程推进、统一经销商匹配口径、补齐资料缺口，并用独立测试与人工复核验证改进。
