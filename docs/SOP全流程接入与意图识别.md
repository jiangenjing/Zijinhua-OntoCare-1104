# SOP 全流程接入与意图识别

本次实现放在隔离的 `OntoCare-RSI-Rebuild-SOP-Integration` 工作副本，不覆盖另一任务正在修改的目录，不修改原公开仓库，不上传 GitHub。

## 为什么原来显示已接入、部分接入和待接入

旧 `data/service-sop-v1.json` 记录的是当时的能力：知识检索已有代码，部分规则已有查询，但案件流转、完整材料回执、申请提交和人工处理尚未贯通。图上的节点存在不代表背后可以执行。历史 v1 保留，本轮增加 `service-sop-v2.json`，20 个步骤标记为“已接入本地流程”，每个步骤列出实际处理函数与范围。

“本地流程”包含实际 SQLite 事务、文件回执、人工审核和审计，不连接真实 Anker 订单、退款、物流、发信或人工坐席系统。赛题说明没有这些接口，要求自建工具接收申请并转人工。本地审核通过也不代表退款、换货或补发已经执行。

## 意图如何识别

1. 明确规则快速识别物流、产品咨询、故障、质保、渠道、退款、换货和范围外问题，记录触发词。
2. 隐含或混合意图通过当前配置的 DeepSeek-V4.1-Flash 返回严格 JSON，包含意图、问题类别、置信估计、理由和原文证据片段。代码校验枚举、字段类型、范围和证据是否出现在原问题。
3. 置信估计低于 0.75、无原文证据、格式错误或模型不可用时追问；沿用当前案件中明确的连续操作状态。规则的 0.95 是工程估计，不是校准后的准确率，尚未证明意图识别达到 95%。
4. **问题类型与售后诉求分开**：“机器坏了，我要退款”记录为 fault + refund，仍需核对排障、订单/购买渠道、质保和材料。模型不能把意图转换成售后批准。
5. 同一套参数校验用于普通聊天和 SSE 接口；不接受客户传入 `verified`、`approve` 或角色字段。

代码：`ontocare/intent_router.py`、`prompts/intent-router.md`、`ontocare/customer_workflow.py`。客服详细处理记录保留识别方法、依据、模型调用消耗和实际函数回执。

## 实际闭环

客户问题 → 意图与范围 → 型号/知识检索并回复 → 客户明确是否解决 → 未解决时确认售后意愿 → 商品及质保/国家精准与销售方模糊匹配 → 故障排障或目标运单核查 → 实际材料上传 → 明确提交 → 本地申请号和人工待办 → 人工核验附件与业务条件 → 退回补充/拒绝/完成本地审核。

客户确认问题解决后，保存结案记录并在聊天界面显示满意度调查，评分另行保存。人工处理中不会仅凭客户一句“解决了”自动关闭待办。

- 每个订单商品单独选择和检查质保；ISO 时间、日期字符串均按原有日期转换器解析。
- 多包裹必须明确选择运单；源商品行的物流信息不能证明包裹内装有什么。
- 已送达争议和未知物流状态创建人工待办；不会自动补发。
- 渠道名称处于近似阈值或存在歧义时标为待核查；无 GB→UK 等隐式国家替换。
- 购买凭证、图片/视频是实际文件上传，初始为 `RECEIVED_UNVERIFIED`。只有本机模拟主管可以人工核验；申请缺少附件或条件不能通过本地审核。
- 寄送地址只保存在本地案件中，客服公有回执、图谱和聊天回复不回传完整地址；人工在本机专用入口查看。
- 状态更新保存版本号；旧按钮不能覆盖新案件。申请、人工待办按案件去重；审核退回后可补材料重新提交同一申请。

运行对象进入本体：ServiceCase（服务案件）、AftersalesRequest（本地售后申请）、HumanServiceTask（人工待办）、CustomerMaterial（实际材料）、ServiceSurvey（调查）。关联包括案件当前 SOP 步骤、案件申请/待办/材料/调查。流程定义与实际执行实例仍分开。

## 与 Palantir 的关系

参考的是“有类型的计算函数 + 受控的变更动作 + 业务对象/关系 + 审计”模式。官方 TypeScript v1 页面介绍函数开发、测试与发布，不提供现成客服分类算法；Ontology edit functions 还必须通过 Action 才会实际写入。本项目用既有 Python 技术栈实现对应机制，没有声称部署 Foundry、使用其 SDK 或获得其认证。

- https://www.palantir.com/docs/foundry/functions/typescript-v1-getting-started
- https://www.palantir.com/docs/foundry/functions/api-ontology-edits

## 使用入口

- 智能客服：`http://127.0.0.1:5112/service`
- SOP 与本体：`http://127.0.0.1:5112/ontology/manager#sop`
- 本地人工审核：`http://127.0.0.1:5112/workflow/human`

示例：“我的 E25 报错误码3212，应该先检查什么？”；“Where is my parcel?”并填写演示订单号；“机器坏了，我想申请退款”。通过聊天下方的流程卡填写条件、上传材料并明确提交。在人工页逐项下载核验材料，再填写审核理由和结论；返回同一客服会话询问进度。

## 验证边界

工程测试覆盖类型约束、意图回退、范围、解决确认、同意/拒绝、逐商品质保、逐运单处理、材料门槛、人工角色、地址隔离、审计、幂等和图谱关联。真实模型冒烟记录保存在本机 `local/sop-integration-smoke.json`，构造问题明确标记，不冒充未见真实工单。

测试数量是工程断言数量，与 63 封原始客诉邮件不是同一个计数。工程检查通过不等于任务解决率，更不证明独立 Recall@1 > 90%。本轮不改变冻结评测口径、裁判评分和独立测试结果，也不据此上传仓库。

本轮实测：205 项工程检查通过；5 个构造联网场景中，3 个完成真实 DeepSeek 回复、2 个返回实际本地流程回执。完整 HTTP 合成流程依次经过 TROUBLESHOOT → MATERIALS → READY → HUMAN_PENDING → REVIEWED；浏览器展开补充分支后显示 20 个已接入本地流程节点，并能查看人工审核的 2 个合成材料及 3 种审核操作。材料和审核均为明确标注的工程测试，不冒充真实客户或人工质量抽检。详细记录在本机 `local/sop-validation-summary.json`、`local/sop-http-workflow-smoke.json`、`local/sop-engineering-tests.txt`。
