# 评测方法与事实边界

## 数据集

- 63 封邮件均为已见首封邮件。原始 SKU／订单元数据作为合法输入，标准答案不传入客服。
- 其中真实 `ticket-028` 明确报告 T2353、3212、已尝试建议及未见阻塞。针对它人工编写的**程序预期**是避免重复同项检查，不代表已由实际业务人员确认解决。
- 30 个宿主构造场景，按十个场景／来源主题组冻结：开发 6、验证 12、最终测试 12。两个语言表达属于同一个语义案例；这里每行是独立指定情境，不把翻译副本累计为额外真实用户。
- 最终场景不传入提案器。但宿主作者编写了全部测试，并在工程预检中执行过最终场景，因此它们不是完全未见或独立第三方盲测。真正的独立真实新增工单数为 0。

## 两种分数

离线分数是端点返回内容上的明确断言：型号、引用哈希、适用范围、工具预算、特定场景行为与政策必要条件。63 封邮件中的多数只有结构和路由检查，没有真实处理结果；因此该通过率很容易较高，绝不能叫客服解决率。

真实模型裁判仅在主模型回答成功且裁判也成功后生成：事实与型号、证据、步骤与历史、业务边界、中英表达，各 0–2 分，要求每项提供理由。总分至少 8 且无硬检查失败才通过。未配置、HTTP 错误、超时、无效 JSON 均不产生有效分数。

独立提示可以减少同一轮上下文影响，但不能消除同源模型偏差。接入后必须披露主模型和裁判实际版本，并执行三次重复及人工对照。

## 比较与门控

普通 RAG、初始本体＋Skill、候选、移除本体、移除 Skill，通过同一个实际 HTTP `/api/chat` 运行。离线实验不作随机采样；不伪造三次相同离线回放为三轮进化。

提案器是本项目的受限确定性程序，由宿主实现。它接收开发／已见回归失败的原始输入和执行状态，提出局部 Skill 修改；不是远端模型训练，也不是开放式、自主修改任意代码。

使用原生 EvoOntology `EvaluationGate.decide_gt` 比较程序断言，并额外按稳定案例 ID 检查任何旧通过变失败。政策／来源变更或不兼容契约会拒绝。当前一次门控包含开发、验证和已见回归，不使用最终组选择候选。

所有实际尝试都记录到 evolution-history；未尝试不填充。停止原因可以是没有额外有依据的假设，不需要凑满三轮。曲线只显示选择案例分数；少量点不能证明收敛、泛化或业务改善。配对 bootstrap 只描述这些相关工程案例内的变化，不是用户总体效果置信保证。

普通 RAG 与消融是本项目的离线控制分支，不是完整真实 LLM RAG 系统的行业基准。移除结构化政策路径会使部分问题转为资料不足；不能据此推断本体比所有 RAG 实现更强。

首轮实验运行代码由 `run-manifest.json` 记录。收尾增加了在线回答契约保护、无模型评测的 incomplete 状态、局部图谱和本体动作关系消费验证；候选 Skill、来源、评测预期未更改。随后对已冻结的两个版本补做全量 HTTP 工程复核，保存为 verification-initial／verification-improved。这次重复不计新进化轮数，也不计新增独立测试；详见 verification.json。

## 人工抽检

提供至少十组打乱 A/B 的回复，版本对应表仅在本地。复核者还需查看原始本地工单和引用知识，记录支持哪一边及理由。未填写真实复核者前始终为 pending；程序或 AI 不代填人工签字。

## 当前未证实

真实问题解决率、多轮真实模型回复质量、真实 LLM Judge 得分、真实模型推理耗时／TTFT、全语种质量、Schema／工具自主进化、递归改进机制本身的进化。不要把离线机制演示扩写成这些结论。
