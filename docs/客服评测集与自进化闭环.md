# 安克智能客服：611题评测、归因与改进说明

本页对应“客服评测与进化”页面及 `evaluation/customer-service-v2` 这一套冻结题集。项目里旧的工程测试、93题实验、其他实验题集与本次611题分别保存，不能把数量相加后称为独立验证。

## 1. 借鉴了 Palantir 的哪些方法

[Create an evaluation suite](https://www.palantir.com/docs/foundry/aip-evals/create-suite) 支持人工用例、从对象集合生成用例，以及精确、自定义和 LLM Judge 评估器。本项目将产品适用范围、知识来源、订单事实、服务动作边界转换成可执行的客服用例。没有在 Foundry 内运行，属于参考其方法的本地实现。

[Run an evaluation suite](https://www.palantir.com/docs/foundry/aip-evals/run-suite) 建议每个依赖LLM的用例至少重复三次，以观察生成不稳定性。本项目先做全量单次运行，再对验证与留出集合做三次重复；开发集单次结果只用于筛查，不声称已经做了全量三次验证。最终共1085次用例执行、1095次HTTP请求；237题中216题三次均通过（91.1%）。界面始终展示已执行次数，未完成的显示待执行。

[Analyze run results](https://www.palantir.com/docs/foundry/aip-evals/analyze-run-results) 强调检查逐例输入、输出、执行轨迹、错误和版本对照。这里可以展开实际回答、引用、图路径、校验和 Judge 理由。通过率不能替代这些证据。

这些官方文档没有规定“必须1000道题”。规模取决于业务覆盖和误差要求。把同一句话改写十次，不会得到十份独立业务知识。这里覆盖19个PN，但样本按产品与来源做覆盖性抽样，不按真实咨询流量加权；整体分数不是线上流量加权预估。

## 2. 本次题集的组成与局限

611题包括：480道知识题、48道缺信息/歧义/越权/未知错误码等边界题、16道订单业务题、63封已见原始工单、4组多轮题。知识题取自240个不同内容哈希的资料组，覆盖19个PN；每组各有中英文改写、来源标识、原文支持片段与参考答案。

按来源组冻结划分为：开发311题、验证118题、留出119题、原始工单回归63题。同一原文的中英文变体不会跨集合，边界题的关联变体也保持同组。知识检索指标的分母分别为288、96、96，其他题型不适合用知识Recall计分。

问题和参考答案由模型依据原文生成，支持片段检查为真实原文子串；这仍不等于独立人工金标准。个别原文适用PN与正文型号可能不一致、同主题资料可能近似重复，因此必须保留人工复核入口。本次不为了提分修改冻结答案或扩大可接受ID集合，发现的标注疑点单独登记。63封工单已被开发人员看到，缺少真实解决结论，只作为回归和证据检查，不计入有标签任务通过率。

## 3. 指标分别说明什么

- **首条命中率/Recall@1**：对单一意图知识题，首条结果是否命中任一可接受的等价来源。这里等价来源代表同一个答案，不是要求同时找回的多个事实。它在统计上也可称 Hit@1，不把它冒充多证据集合的完整召回率。另报@3、@6、MRR、语言切片与来源组bootstrap区间。
- **有标签任务通过率**：Judge判断答案正确、政策安全、历史一致，代码检查期望决策和引用等条件均通过。知识题按参考答案，边界和多轮题按明确的期望决策标签计分。主分母包含所有已执行的有标签任务，Judge未完成者不算已验证通过，并单列数量；只有缺少独立解决标签的63封已见工单排除。它是离线任务效果，不能直接宣称生产问题解决率。
- **Faithfulness**：独立评估调用拆分原子声明，计算证据支持声明/全部声明。Judge和生成器当前使用相同网关与模型系列，存在共同偏差，不是独立人工认证。
- **RAGAS**：在隔离环境实际运行Ragas 0.4.3的Faithfulness、ContextPrecision、ContextRecall；上下文是实际检索出的完整原文，不只挑选已引用的文章。12题固定配对抽样单独报告样本量，不推广为全量质量。Ragas没有统一官方“综合分”，因此不伪造一个。本轮固定12题配对抽样实际结果：Faithfulness 82.2%→89.3%，Context Precision 72.1%→91.9%，Context Recall 91.7%→100%。这只是抽样改善证据，Faithfulness仍有不足，不能描述成全量无幻觉。上下文保留实际发给回答模型的标题、适用PN与全部检索原文；此前只传正文导致标题中的型号/错误码信息缺失的评估尝试已单独留档。
- **效率**：完整HTTP P50/P99、单独的图检索和检索阶段耗时、回答链与Judge Token。报告缓存状态；预编码向量的离线排序耗时不冒充端到端时延。小样本P99只作描述，不能当SLA。知识评测题的查询翻译已在检索实验中预热，因此这些HTTP时延属于相应缓存条件；另留一条新中文查询的冷启动样例，不能将单条样例称为冷P50/P99。网关实际单价未提供，金额留空。
- **业务**：真实转接率、CSAT、重复咨询率、真实解决率需要转接回执、问卷、客户关联和关闭工单。现有资料不足，均显示未测。“人工核查建议率”只是代理指标。后续生产采集应包含：客户确认解决/关闭时间、真实转接回执、1—5分问卷及回应率、同客户同问题7天内再次联系标识。CSAT可按4—5分问卷数/有效问卷数，重复咨询率按发生再次联系的问题数/已结案问题数；时间窗和口径需冻结。

增加幻觉检查通常会**增加时延**，有机会提升忠实度。售后优先级是正确性、速度、成本；涉及退款/换货时，还需满足操作授权边界。

## 4. 本轮实际改动

1. 原始英文资料对中文查询不友好。开发集原检索首条命中70.5%，其中中文48.6%、英文92.4%。新增仅用于搜索的英文查询改写，模型只看客户问题，不接触参考答案或目标文档ID；保留型号、错误码、数值条件、否定和已完成动作。异常回退原始查询，翻译缓存、调用时间与Token可追溯。
2. 原RRF把标题命中与长正文中的常见排障词混合。开发集比较有限的排序候选后，采用标题向量0.82、正文向量0.10、标题BM25饱和分数0.08。型号/错误码仍是硬边界，找不到合适型号或代码时追问或保留未知。
3. 对失败回答归因后，Prompt增加“首句回答具体问题、保留例外条件、仅陈述有证据的事实、不要添加无关售后保证”；使用引用/型号/执行承诺校验。不合格时最多一次带校验原因的重写，再失败则保底，未放宽校验来提高分数。
4. 修复把 `T8170 error 3212` 中的8170误读为错误码的问题。增加独立图检索计时、查询改写Token记录和逐题追踪。
5. 为避免共享工作区同时修改检索代码污染运行，本次验证代码隔离为 `customer_agent.py`、`customer_retrieval.py`、`customer_ranking.py`、`customer_query_rewrite.py`。一次模块冲突产生的HTTP失败作为基础设施失败留档，另起冻结运行重测，不能混进产品通过率。

检索结果：新方案开发92.0%、验证91.7%，冻结后留出95.8%（92/96），留出中文93.8%、英文97.9%，@3与@6均100%。这是该题集的点估计，区间与逐题结果在评测页；不能保证线上始终≥90%。全量首次有标签任务通过522/548（95.3%），按划分看开发301/311（96.8%）、验证105/118（89.0%）、留出116/119（97.5%）。验证集仍存在型号冲突、答复不足与Judge疑点，完整失败记录保留。声明级忠实度为3431/3797（90.4%）。检索达标不代表所有分项都达到90%，这些离线分数也不等于真实客户解决率。

## 5. 图搜索在客服里做什么

流程是：客户问题 → 型号/商品范围 → 必要的英文查询改写 → 混合检索 → 知识节点作为种子 → 型号范围内两跳BFS → 读取关联对象、动作、来源映射、约束 → 代码执行服务边界判断 → 模型组织答复 → 引用与安全校验。

图最多30个概念节点、6个知识种子，不从产品大枢纽扩散到全部故障。图帮助查适用范围和可追溯路径，不能仅凭“有连接”就认定政策成立、故障因果成立或售后获批。当前没有声称使用通用OWL推理机或因果推理。

Service Ontology表达产品、知识、客户订单、包裹、销售方与事实；Decision Ontology表达服务条件、未知项、适用规则、下一步和动作边界。MCP将这些受限读查询和受控Action暴露给外部Agent；MCP本身不会自动产生可靠客服，Agent还需要会话、检索、执行权限、审计和评测。

## 6. 自进化闭环和停止条件

冻结来源与题集 → 原版实测 → 逐题归因 → 提出少量有理由的候选 → 开发集实验 → 验证集筛选 → 冻结实现 → 留出检索与完整回答验证 → 对失败保留证据 → 发布通过版本。

本轮检索停止条件为冻结留出集首条命中点估计≥90%，且作用域/来源/操作边界回归不能放松。留出集只用来检查冻结候选，不继续围绕留出题调参。未来如果用其失败题做开发，应另采全新的来源组作留出集。

本轮没有训练模型权重，没有奖励模型，没有RLHF。主效果分数按每题首次执行等权统计，三次均通过率另报；不会因验证/留出比开发集多跑两次而改变主分数的题型权重。查询翻译、Prompt修改、检索排序和有限校验重写属于工作流优化。MCP的search_knowledge也复用该检索模块，外接Agent仍需单独验证其完整对话效果，不能照搬本网页Agent的分数。今后若积累了经过人工复核的好坏答案偏好对，可以评估DPO/SFT，但不能把当前LLM自评分当作已完成RLHF。
