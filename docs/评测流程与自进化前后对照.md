# 安克客服评测：数据构建、评分、自进化与前后对照

本文只引用本轮 `customer-service-v2` 的611题与已保存接口结果。其他实验单独统计。数据集、回答、Judge结果和前后版本均已留档，本次展示不修改原分数。

## 先回答“解决率是多少”

- **离线任务首次通过率：522/548 = 95.26%。** 548题有参考答案或期望决策标签；63封已见原始工单缺少独立解决结果，不进入此分母。
- **三次稳定通过率：216/237 = 91.14%。** 同一道题三次均通过才算稳定通过。
- **真实客户解决率、自动解决率：未测。** 正确追问、拒答、建议人工核查可以完成离线用例要求，但不能证明实际客户问题已经解决。
- **能直接比较的任务改善：同40题，35/40（87.50%）→40/40（100%），+12.50个百分点。** 这40题是开发调试样本，按当前统一评分规则包含知识参考与期望决策标签。它说明已知问题修正有效，不代表全量或生产100%。
- **原版完整548题任务通过率没有测得。** 因此不能把原版40题87.5%与新版548题95.3%相减后声称全量提升。

## 2. 业务数据集与评测集是两种东西

业务底座来自赛题五个sheet：客诉工单、订单、Robovacs Q&A、Breast Pump Q&A、国家/经销商名单。知识原文有875条、872条客户可见；业务对象包括产品型号、知识、订单、逐商品记录、包裹、销售方、服务规则和操作边界。

底座构建流程：原文件 → 保留sheet/行号/哈希 → 处理真实合并单元格与重复内容 → 识别现实业务对象和关系 → 标记适用PN、可见性和未知字段 → 进入本体与检索库。不能把表格一行整体当成业务对象，也不能从缺失数据推断授权、币种或包裹内容。

评测集构建流程：从上述底座挑选业务任务 → 生成或整理问法 → 给出参考答案/可接受来源/期望行为 → 校验原文支持片段 → 按来源组划分集合 → 冻结题集与评分规则 → 执行版本对比。

| 题型 | 数量 | 构建方式 | 主要检查 |
|---|---:|---|---|
| 知识问答 | 480 | 240个内容来源组，每组中英文各1题，覆盖19个PN | 检索、答案正确、条件与忠实度 |
| 边界场景 | 48 | 12个基础场景各4种前缀变体，同组划分 | 缺型号/订单、未知错误码、越权退款、渠道未知 |
| 订单业务 | 16 | 根据16个样例订单构建查询任务 | 逐商品状态、包裹、来源金额和未知内容 |
| 多轮场景 | 4组 | 已完成检查、重启后仍异常、订单追问、切换型号 | 状态继承、避免重复步骤、切换清空旧状态 |
| 已见工单 | 63 | 原始第一封客户邮件，脱敏展示 | 真实表达回归与证据检查，无真实解决金标准 |

划分：开发311、验证118、留出119，另63题回归。知识来源组为144/48/48，对应知识题288/96/96。同原文的中英文问法不跨集合；边界前缀变体也不跨集合。题量覆盖19个型号，但不是按真实咨询流量加权，不能等同生产分布。当前分组按完全相同内容哈希，近似重复和同主题文章仍需进一步语义去重与人工检查。

每题保存：题目ID、来源组、集合、型号、问题/多轮内容、可接受来源ID、参考答案或期望决策、原文支持片段、来源sheet/行号/哈希。参考答案与Gold文档标注只交给评估器。Agent可见检索到的文档和引用ID，但不获得“测试题→标准文档”的映射。知识检索题提供明确PN，缺型号/歧义场景另测边界正确率。

本次机器生成问法与参考答案，检查支持片段确实存在原文；这还不等于人工确认答案完整、来源适用无冲突。16条型号疑点已单独登记，未通过删题或改Gold提高分数。行业完整SOP应再经过客服专家复核与争议裁定，并扩充真实多轮场景；本次多轮仅4组，覆盖仍有限。

## 3. 实际评测过程与评分

1. 冻结题集、来源、模型、Prompt和检索版本。
2. 原版先跑检索基线与40题真实答复调试样本。
3. 检查每道失败的输入、适用范围、检索结果、回复与Judge理由。
4. 只依据开发集失败提出候选：查询改写、型号校验修复、排序和答复约束。
5. 开发集比较有限候选，验证集筛选；通过后冻结参数。
6. 在留出集评测；不继续围绕留出失败题调参。
7. 新版全611题真实接口回答；验证与留出共237题再各增加2次，合计1085次用例执行、1095次HTTP请求。
8. 保存所有回答、原始评分、失败归因和版本记录。复用缓存的r0只算原来的1次，不作为新执行。

**任务通过采用联合条件，不能靠几个平均分掩盖越权：**

`任务通过 = 答案正确 ∧ 政策安全 ∧ 历史一致 ∧ 期望决策匹配（如有） ∧ 引用/来源/工具预算检查通过`

代码负责确定性检查；LLM Judge评估答复语义、声明支持、历史和政策；Ragas独立计算检索上下文与回答分项。Judge与生成器使用同模型系列的不同调用，存在相关偏差。曾出现Judge把上轮旧型号问题误当作本轮应答要求的情况，原始扣分仍保留，另列评估器校准队列。

| 层面 | 指标 | 定义或解释 |
|---|---|---|
| 任务 | 首次通过率、各题型/集合通过率 | 按每题首次执行等权统计，不用重复次数改变题型权重 |
| 稳定性 | 三次均通过率 | 三次都通过的题数/做满三次并评分的题数 |
| 检索 | 首条命中、@3/@6、MRR | 本轮Recall@1指首条命中任一等价来源，即query-level Hit@1；不是多证据集合完整召回 |
| 答案 | 声明级Faithfulness | 有证据支持的原子声明/所有原子声明；零声明单列，不当作100% |
| RAGAS | Faithfulness、Context Precision、Context Recall | 固定12题配对抽样，真实Ragas运行；无自设统一综合分 |
| 效率 | 完整HTTP P50/P99、图查询耗时、Token | 查询改写已部分预热；图查询区分缓存命中/未命中；Judge消耗单列 |
| 业务 | 真实解决率、自动解决率、转接率、CSAT、重复咨询率 | 未采集真实业务闭环、回执、问卷，均未测 |

## 5. 自进化的具体体现

| 候选 | 从失败中发现什么 | 实际修改 | 开发/验证首条命中 |
|---|---|---|---|
| 原版 | 中文查询匹配英文资料较差 | 记录BM25+E5+RRF基线 | 70.49% / 63.54% |
| 候选1 | 跨语言词法召回不足 | 只把搜索问题改写为英文，保留型号、错误码和否定 | 89.24% / 88.54% |
| 候选2 | 型号紧邻中文时被错误校验 | 修复型号边界识别 | 89.58% / 88.54% |
| 候选3 | 正确资料在Top6但首位不准 | 标题向量0.82+正文向量0.10+标题BM25 0.08 | 92.01% / 91.67% |
| 冻结检查 | 检查未参与调参的来源组 | 留出检索、完整回答与重复执行 | 留出95.83%，三次任务稳定91.14% |

回答层同时调整Prompt v3：先直接回答、保留条件、不增加无证据补充；输出引用/型号/业务承诺校验失败时最多重写一次，失败仍保底。修复错误码解析，并记录额外改写调用与图检索耗时。MCP知识工具复用相同检索算法；外接Agent的完整效果仍应单独评测。

真实开发Bad Case：客户问“T2352拖地后污水箱水比清水箱少，为什么？”原版未检索到对应资料，引用“污水箱已满”检查并表示无法解释。新版首条命中 `qa-ba9360f02f65`，依据原文说明清水部分被地面吸收，收集污水少于用水正常；该题Judge由未通过变为通过。它展示开发问题修复，不充当未见数据证明。

图搜索负责型号范围内两跳BFS证据导航，最多30个概念节点、6个知识种子；业务规则核对服务条件和已完成步骤。图连接本身不能证明故障因果、政策适用或售后批准。

**本轮是评测驱动的受控迭代。** 运行、评分、日志与汇总可以自动执行；候选Prompt和算法修改由开发过程提出和实施。没有常驻无人改代码/自动上线机制，也没有训练模型权重、奖励模型或RLHF。会话记忆保留当前型号与已做步骤；评测反馈负责推动下一版本，两者分别保存。

后续持续闭环：生产会话与结果 → 客服复核Bad Case → 加入开发回归队列 → 提出候选 → 独立验证 → 新留出集 → 受控发布。若使用当前留出失败题改进，必须建立新的未见留出集；不能在同一留出集上反复追分。

真实解决率应先冻结口径：按唯一客户问题统计，在约定时间窗内有解决确认/可靠结果，区分人工介入并追踪重开；CSAT、转接和重复咨询分别采集。平台对自动/验证/闭环解决的定义不同，参照[Zendesk对不同解决指标的区分](https://support.zendesk.com/hc/en-us/articles/11046706190746-Understanding-the-AI-agents-dashboard-in-analyst-copilot-EAP)，不要将离线答题得分直接替代生产业务结果。
